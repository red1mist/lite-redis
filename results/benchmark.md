# lite-redis benchmark results

- Generated by `test/bench.py` (`make bench`), 2026-11-24 10:14 UTC
- Host: Apple M1 (8 cores, 8 GB); Docker Desktop Linux VM (aarch64, kernel 6.10.14-linuxkit, 8 vCPUs)
- Servers: lite-redis (-O2) vs Redis server v=7.0.15, each pinned to core 0, no persistence
- Client: redis-benchmark (same version) pinned to cores 2-7, over loopback
- Each cell: **median of 3 runs** (min–max in brackets), runs alternating between servers
- Latencies are redis-benchmark's per-request p50/p99 in ms
- Each run lasts ~8-12 s (redis-benchmark's completion timer is coarse; short runs quantize the result)
- Server CPU: lite-redis's CPU time during the run, split into user space (our code) and kernel (syscalls, TCP)

Workloads:

- **default client (client-bound)**: plain `redis-benchmark -t set,get -c 50`: one client thread, which can't saturate either server; `redis-benchmark -t set,get -n 2500000 -c 50`
- **saturated, no pipelining**: 50 connections, 1 request in flight each, client with 2 threads; `redis-benchmark -t set,get -n 5000000 -c 50 --threads 2`
- **pipelined -P 16**: 16 requests per round trip: syscall cost amortized over 16 commands; `redis-benchmark -t set,get -n 30000000 -c 50 -P 16 --threads 2`
- **1 KB values**: 1024-byte values instead of 3 bytes; `redis-benchmark -t set,get -n 4000000 -c 50 -d 1024 --threads 2`
- **1000 clients**: 1000 concurrent connections on one thread; `redis-benchmark -t set,get -n 4000000 -c 1000 --threads 2`
- **SET with TTL, 1M random keys, -P 16**: every write inserts/updates the expiry heap (lite) / expires dict (Redis); `redis-benchmark -n 8000000 -r 1000000 -c 50 -P 16 --threads 2 SET key:__rand_int__ xxx EX 100`

Notes:

- With the default single-threaded client the servers sit well below 100% CPU: that row measures
  redis-benchmark, not the server. The saturated rows are the meaningful comparison.
- Most of lite-redis's CPU time is in the kernel (`read`/`write`/`epoll_wait` and the TCP stack);
  command execution itself is a small fraction. Pipelining is fast because it amortizes those syscalls.
- Numbers come from a laptop VM over loopback; they are for comparison on identical conditions,
  not absolute claims about either server. Real Redis does more work per command (stats,
  keyspace notifications, replication/persistence hooks, many more data types).
